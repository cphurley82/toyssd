# SSD Simulator Design Document

## 1. Overview

This document describes the design for `toyssd`, a modular solid-state drive (SSD) simulator implemented as an importable Python package backed by SystemC TLM‑2.0 models. The simulator targets rapid prototyping of SSD behaviors while maintaining enough fidelity to support future firmware experimentation. Clean Code principles guide structure and readability across C++ and Python components.

## 2. Goals

- Provide a Python-first SSD simulation API that instantiates SystemC 3.0.1 models via PySysC (branch `fix-pyeval-init`).
- Model a minimal SSD datapath: `host` → Simple NVMe-like TLM extension → `ssd_controller` → Simple NAND ONFI-like TLM extension → `nand`.
- Support blocking transport-only TLM2 interactions for deterministic behavior.
- Supply standalone GoogleTest suites for each SystemC model and ensure Python bindings can instantiate each model in isolation.
- Offer a simple NAND visualization reminiscent of Norton Disk Doctor’s defragmentation view to illustrate block usage.
- Integrate with modern tooling: C++20, CMake, clang-format, clang-tidy, cpplint, Invoke for automation, uv for Python dependency management.
- Establish a foundation for long-term integration of the DBT-RISE RISC-V core to run Zephyr-based firmware inside the simulation.

## 3. Non-Goals (Initial Release)

- Cycle-accurate NVMe protocol compliance or timing fidelity.
- Detailed NAND flash physics (reserved for long-term roadmap).
- Multi-core host or controller models.
- Hardware co-simulation or FPGA acceleration.
- Full firmware stack execution (reserved for long-term roadmap).

## 4. High-Level Architecture

```
Python API (toyssd package)
├── Simulation orchestrator (Invoke tasks & Python entrypoints)
├── Visualization (ASCII defrag view)
└── PySysC bindings
    └── SystemC kernel (C++20)
        ├── host model
        ├── ssd_controller model
        └── nand model
```

Communication channels:

- Host ↔ Controller: NVMe-inspired blocking transport transactions carrying an extension with namespace, command opcode, logical block address (LBA), and data payload descriptors.
- Controller ↔ NAND: NAND operation extension encapsulating die/channel, page/block addresses, command type (read/write/erase), and simple status codes.
- A lightweight event logger captures transaction flow for visualization and debugging.

## 5. Component Design

### 5.1 Python Package (`toyssd`)

- `toyssd/__init__.py`: exports high-level API (`ToySSD`, `Host`, `Controller`, `Nand`, `run_simulation`).
- `toyssd/sim.py`: orchestrates SystemC kernel startup via PySysC, manages threading, and exposes synchronous methods (`submit_io`, `step`, `shutdown`).
- `toyssd/visualization.py`: renders NAND block states using ASCII art inspired by the Norton Disk Doctor defrag display. Internally stores block metadata (free/used/bad/tested) and updates based on NAND transactions.
- `toyssd/config.py`: holds configuration dataclasses (geometry, timing placeholders, log configuration).
- `toyssd/tasks.py`: Invoke tasks for building the C++ core, running simulations, formatting, linting, and tests.
- `toyssd/_bindings/`: C-extension module generated by PySysC exposing constructors and adapters for each SystemC component.

### 5.2 SystemC Models

All models follow Google C++ style, compile under C++20, and use blocking transport via `b_transport`. Each model exposes configuration ports and tracing hooks.

- `host`:
  - Generates NVMe-like submission queues.
  - Implements a test harness to send read/write/flush commands through the TLM socket.
  - Receives completion status via a blocking backward path.
  - Configurable via simple scriptable workload descriptions.

- `ssd_controller`:
  - Converts host commands into NAND operations.
  - Maintains logical-to-physical mapping in memory (simple linear mapping for initial milestone).
  - Dispatches commands sequentially to NAND model; implements minimal error handling.
  - Emits events for visualization (e.g., block allocated, erased, marked bad).

- `nand`:
  - Emulates an array of blocks/pages with state tracking (unused/used/bad/testing).
  - Responds to NAND extension commands with deterministic latencies (configurable via parameters).
  - Updates visualization state and optionally persists snapshots for debugging.

### 5.3 TLM Extensions

Define two custom blocking transport payload extensions:

1. `NvmeCommandExtension`
   - Fields: command_id, opcode, namespace_id, lba, length, data_ptr (host-managed buffer handle), status.
   - Used in host ↔ controller transport.

2. `NandCommandExtension`
   - Fields: command_type (READ/PROGRAM/ERASE/MARK_BAD), channel, die, block, page, data_ptr, result_code.
   - Used in controller ↔ NAND transport.

Both extensions derive from `tlm::tlm_extension` and include clone/copy hooks. Payloads do not model timing annotations beyond simple blocking delays applied by the callee.

### 5.4 Visualization Module

- Implemented in Python with curses-compatible ASCII rendering.
- Receives events via an async-safe queue from the SystemC side (PySysC callback) or through polled REST-style calls.
- Visual layout mirrors Norton Disk Doctor: rows of block glyphs with legend, progress, and status fields.
- Export screenshot-like frames for automated tests (text-based golden files).

## 6. Build & Tooling Strategy

 - **CMake** (minimum version 3.23) drives C++ build. Fetch external dependencies (`SystemC 3.0.1`, `PySysC`, `GoogleTest`) via `FetchContent`/`ExternalProject` rather than git submodules.
- **uv** manages Python environments and dependencies (Invoke, curses support, rich for CLI rendering if desired).
- **Invoke tasks**:
  - `invoke bootstrap`: install/verify SystemC, PySysC build, configure uv environment.
  - `invoke build`: run CMake configure & build for core library.
  - `invoke test`: execute GoogleTest suites and Python unit tests.
  - `invoke lint`: run clang-format (check), clang-tidy, cpplint, and Python linters (pylint/flake8).
  - `invoke viz-demo`: launch sample simulation + visualization.
- Integrate `gcovr` to generate unified C++ code coverage reports; expose results via Invoke (`invoke coverage`) and archive outputs for CI.
- Treat compiler warnings as errors for all internal targets (`-Werror` via `target_compile_options`), while leaving third-party dependencies at their default warning settings.
- **Formatting & Static Analysis**:
  - Maintain `.clang-format` aligned with Google C++ style.
  - Configure `clang-tidy` targets in CMake (`CMAKE_CXX_CLANG_TIDY`).
  - Integrate `cpplint` via Invoke to enforce Google style specifics.
  - Python: leverage `pylint` plus `ruff` for formatting and linting while conforming to Google Python style.

## 7. Testing Strategy

- **C++ Unit Tests**:
  - Each model resides in `src/<component>` with a matching `tests/<component>_test.cc`.
  - Use `gtest_main` and the [tlm2-gtestbench](https://github.com/cphurley82/tlm2-gtestbench) patterns to instantiate SystemC kernels inside GoogleTest fixtures.
  - Provide mocks/stubs for downstream components when testing in isolation (e.g., host tests stub controller responses).

- **Python Tests**:
  - Use `pytest` for API-level validation (instantiation, simple I/O submission, visualization snapshot).
  - Ensure Python tests run after building bindings (Invoke orchestrates dependency order).

- **Integration Tests**:
  - Combine all three models to execute scripted workloads (sequential reads/writes, bad block handling).
  - Validate visualization output via deterministic text frames.

- **Continuous Verification**:
  - GitHub Actions workflow runs on push/PR to execute Invoke build, test, lint, format-check, and coverage tasks.
  - Track `gcovr` coverage reports in CI dashboards; set an aspirational target of >90% line coverage while allowing a lower temporary threshold during early development iterations.

```text
toyssd/

    └── ssd_sim_design.md
```

`uv` metadata (`pyproject.toml`) lives at the repository root, ensuring consistent Python environments. C++ dependencies are retrieved during CMake configure time via `FetchContent`.

## 9. Development Workflow

1. Clone repo and run `invoke bootstrap` to configure SystemC/PySysC toolchains and prepare FetchContent caches.
2. Configure build: `invoke build --config Debug` (task wraps `cmake -B build/debug -DCMAKE_BUILD_TYPE=Debug`).
3. Run tests frequently (`invoke test`).
4. Format & lint before commits (`invoke lint`).
5. Use clang-tidy `-checks=google-*,performance-*,readability-*` with suppressions documented in `.clang-tidy`.
6. When modifying visualization, update snapshot baselines and re-run integration tests.

## 10. Initial Milestones

1. **Infrastructure**: Set up CMake build, PySysC bindings, uv environment, Invoke tasks, formatting configuration.
2. **Model Skeletons**: Implement host, controller, and NAND classes with baseline blocking transport interactions; add GoogleTests verifying socket connectivity.
3. **Visualization MVP**: Render single-drive geometry with sequential write workload, mimic Norton Disk Doctor style.
4. **Integration Demo**: Python script demonstrating host workload submission and visualization updates.
5. **Extended Features**: Error injection, bad block handling, config-driven workloads.
6. **Roadmap**: Prototype integration with DBT-RISE RISC-V core and Zephyr firmware boot flow.

## 11. Future Enhancements

- Introduce timing annotations and bandwidth modeling.
- Add wear leveling, garbage collection, and FTL policies.
- Integrate trace import/export (e.g., blktrace, FIO).
- Provide REST/gRPC control plane for external orchestration.
- Host co-simulation with Verilator or QEMU to drive realistic command streams.
- Multi-die NAND model with parallelism and contention modeling.

## 12. Risks & Mitigations

- **PySysC compatibility drift**: Track upstream changes; pin commit hash from `fix-pyeval-init` branch and add automated smoke tests.
- **Visualization performance**: Cache rendering state and throttle updates for large geometries; offer headless mode.
- **SystemC dependency management**: Document bootstrap process, supply scripts to build SystemC 3.0.1 locally.
- **Long-term firmware integration complexity**: Isolate interfaces and maintain clear separation between TLM models and higher-level firmware harness.

## 13. Open Questions

- Should visualization live entirely in Python, or do we need C++ event hooks for performance?
- What level of NAND geometry detail (planes, wordlines) is required for target use cases?
- How will firmware integration synchronize with the existing host model (e.g., NVMe vs. custom command set)?
- Do we need a configuration DSL or rely on Python builder patterns?
