# toyssd - SSD Simulator Design Document

## 1. Overview

This document describes the design for `toyssd`, a modular solid-state drive (SSD) simulator implemented as an importable Python package backed by SystemC TLM‑2.0 models. The simulator targets rapid prototyping of SSD behaviors while maintaining enough fidelity to support future firmware experimentation. Clean Code principles guide structure and readability across C++ and Python components.

## 2. Goals

- Provide a Python-first SSD simulation API that instantiates SystemC 3.0.2 models via PySysC (branch `fix-pyeval-init`).
- Model a minimal SSD datapath: `host` → Simple NVMe-like TLM extension → `controller` → Simple NAND ONFI-like TLM extension → `nand`.
- Support blocking transport-only TLM2 interactions for deterministic behavior.
- Supply standalone GoogleTest suites for each SystemC model and ensure Python bindings can instantiate each model in isolation.
- Offer a simple NAND visualization reminiscent of Norton Disk Doctor’s defragmentation view to illustrate block usage.
- Integrate with modern tooling: C++20, CMake, clang-format, clang-tidy, cpplint, Invoke for automation, uv for Python dependency management.
- Establish a foundation for long-term integration of the DBT-RISE RISC-V core to run Zephyr-based firmware inside the simulation.

## 3. Non-Goals (Initial Release)

- Cycle-accurate NVMe protocol compliance or timing fidelity.
- Detailed NAND flash physics (reserved for long-term roadmap).
- Multi-core host or controller models.
- Hardware co-simulation or FPGA acceleration.
- Full firmware stack execution (reserved for long-term roadmap).

## 4. High-Level Architecture

```text
Python API (toyssd package)
├── Simulation orchestrator (Invoke tasks & Python entrypoints)
├── Visualization (ASCII defrag view)
└── PySysC bindings
    └── SystemC kernel (C++20)
        ├── host model
        ├── controller model
        └── nand model
```

Communication channels:

- Host ↔ Controller: NVMe-inspired blocking transport transactions carrying an extension with namespace, command opcode, logical block address (LBA), and data payload descriptors.
- Controller ↔ NAND: NAND operation extension encapsulating die/channel, page/block addresses, command type (read/write/erase), and simple status codes.
- A lightweight event logger captures transaction flow for visualization and debugging.

## 5. Component Design

### 5.1 Python Package (`toyssd`)

- [`toyssd/__init__.py`](../python/toyssd/__init__.py): exports high-level API (`ToySSD`, `Host`, `Controller`, `Nand`, `run_simulation`).
- [`toyssd/sim.py`](../python/toyssd/sim.py): orchestrates SystemC kernel startup via PySysC, manages threading, and exposes synchronous methods (`submit_io`, `step`, `shutdown`).
- [`toyssd/visualization.py`](../python/toyssd/visualization.py): renders NAND block states using rich-powered ASCII graphics inspired by the Norton Disk Doctor defrag display. Internally stores block metadata (free/used/bad/tested) and updates based on NAND transactions.
- [`toyssd/config.py`](../python/toyssd/config.py): holds configuration dataclasses (geometry, timing placeholders, log configuration).
- [tools/invoke_tasks.py](../tools/invoke_tasks.py) and [tasks.py](../tasks.py): Invoke tasks and entrypoint for build/test/lint.
- [`toyssd/_bindings/`](../python/toyssd/_bindings/): C-extension module generated by PySysC exposing constructors and adapters for each SystemC component.

#### 5.1.1 Python API Example

```python
from toyssd import ToySSD, NandGeometry, SimConfig, Workload

# Configure simulation
geometry = NandGeometry(
    capacity_gb=1,
    dies=4,
    blocks_per_die=1024,
    pages_per_block=256,
    page_size_bytes=16384
)

config = SimConfig(
    nand_geometry=geometry,
    enable_visualization=True,
    log_level="INFO"
)

# Create and initialize simulator
sim = ToySSD(config)

# Define workload patterns (host generates I/O based on patterns)
workload = Workload.sequential_write(
    start_lba=0,
    length_gb=0.5,
    block_size_kb=128
)

# Run workload for specified duration or until completion
sim.run_workload(workload, duration_ms=1000)

# Add another workload phase
workload2 = Workload.random_read(
    lba_range=(0, sim.capacity_lba),
    io_count=10000,
    block_size_kb=4,
    queue_depth=32
)

sim.run_workload(workload2, duration_ms=500)

# Display visualization showing block states after workloads
sim.viz.render()
sim.viz.save_snapshot("output/state.txt")

# Query statistics
stats = sim.get_stats()
print(f"Total writes: {stats.total_writes}")
print(f"Total reads: {stats.total_reads}")
print(f"Write amplification: {stats.write_amplification:.2f}")

# Graceful shutdown
sim.shutdown()
```

#### 5.1.2 Threading Model and Event Propagation

SystemC enforces **single-threaded execution** semantics. The Python API uses a **synchronous, Python-controlled execution model**:

**Execution Model:**

- SystemC kernel executes in the **same thread** as Python.
- Python controls simulation time advancement by calling `sc_start(duration)` with explicit time quanta.
- `run_workload(workload, duration_ms)` translates to `sc_start(sc_time(duration_ms, SC_MS))`.
- Host model generates I/O transactions based on workload parameters during simulation execution.
- Between `sc_start()` calls, Python can query state, update visualization, and modify workload parameters.

**Event Propagation:**

- SystemC models emit events to a **C++ event buffer** during `b_transport` execution.
- After each `sc_start()` returns, Python drains the event buffer via PySysC bindings.
- Event buffer uses simple `std::vector<Event>` that gets cleared after Python processes events.
- No threading or synchronization primitives needed.

Python orchestration contract:

- `run_workload(workload, duration_ms)` and `step(duration_ms)` advance time via `sc_start(sc_time(duration_ms, SC_MS))`.
- Returns a summary with `{ ios_completed, events_drained, sim_time_ms }` for observability.
- Error modes: raise `SimulationError` on non-OK TLM responses; raise `CommandError` on invalid parameters; raise `HardwareError` for device faults signaled by extension statuses.

**Memory Management:**

- **Metadata-only approach**: No actual host data is transferred across Python/C++ boundary.
- Host model uses **synthetic data patterns** (e.g., sequential counter, LBA-based hash) for write verification.
- Read verification compares expected pattern against returned pattern using metadata (LBA, length, pattern type).
- Extensions carry only **command metadata** (LBA, length, pattern_id) and status codes.
- Simple copy semantics: Python passes primitives (integers, enums); no buffer management required.

**Execution Flow:**

```text
Python                          SystemC Kernel
──────                          ──────────────

ToySSD.__init__()     ───►      sc_core::sc_report_handler::initialize()
                      ───►      Construct host, controller, nand models

run_workload(params)  ───►      host.configure_workload(params)
                      ───►      sc_start(duration)
                                  │
                                  ├─► Host generates I/O (pattern-based)
                                  ├─► b_transport(NvmeCmd)
                                  ├─► Controller FTL mapping
                                  ├─► b_transport(NandCmd)
                                  └─► Events logged to buffer
                      ◄───      
drain_events()        ───►      Get event buffer, copy to Python
viz.update(events)              
                                
step(duration_ms)     ───►      sc_start(sc_time(duration_ms, SC_MS))
                                  └─► Continue simulation
```

### 5.2 SystemC Models

All models follow Google C++ style, compile under C++20, and use blocking transport via `b_transport`. Each model exposes configuration ports and tracing hooks.

- `host`:
  - Generates NVMe-like I/O based on **workload specifications** (sequential/random, read/write mix, queue depth, block sizes).
  - Implements parameterized workload generators: sequential write/read, random write/read, mixed patterns.
    - Sends commands through TLM socket using blocking transport with NVMe command extensions.
    - Tracks pattern metadata for verification: writes record pattern type/seed, reads validate against expected pattern.
    - Receives completion status via b_transport return path (response status + extension status).
    - Configurable via Python API: `Workload.sequential_write(...)`, `Workload.random_read(...)`, etc.
    - Initial release assumes `queue_depth = 1` end-to-end (host and controller).
    - Alignment and capacity rules: `block_size_kb` must be divisible by `sector_size_bytes`; writes that span pages are split internally; capacity overruns raise `CapacityError`.

- `controller`:
  - Converts host NVMe commands into NAND operations through Flash Translation Layer (FTL).
  - Direct-mapped addressing (LBA → fixed physical block/page) for initial validation.
  - Dispatches commands sequentially to NAND model.
  - Emits events for visualization (e.g., block allocated, erased, marked bad, garbage collection activity).

- `nand`:
  - Emulates an array of blocks/pages with state tracking following real NAND constraints.
  - Enforces NAND programming rules: **blocks must be erased before programming**, pages within a block must be programmed sequentially (lower to higher page numbers), and each page can only be programmed once per erase cycle.
  - Responds to NAND extension commands with deterministic latencies (configurable via parameters).
  - State machine per block: `FACTORY_BAD` | `ERASED` → `VALID` (on successful program) → `INVALID` (on controller invalidation) → `ERASED` (on erase) | `RUNTIME_BAD` (on erase/program failure).
  - Simulates realistic failure modes: program failures (configurable error rate), erase failures after wear threshold, and read disturb (optional).
  - Updates visualization state via event emission and optionally persists snapshots for debugging.

### 5.3 TLM Extensions

Define two custom blocking transport payload extensions:

1. `NvmeCommandExtension`
   - Fields: command_id, opcode, namespace_id, lba, length, pattern, pattern_seed, status.
   - Used in host ↔ controller transport.

2. `NandCommandExtension`
   - Fields: command_type (READ/PROGRAM/ERASE/MARK_BAD), channel, die, block, page, plane, pattern, pattern_seed, length_bytes, status.
   - Used in controller ↔ NAND transport.

Both extensions derive from `tlm::tlm_extension` and include clone/copy hooks. Payloads do not model timing annotations beyond simple blocking delays applied by the callee.

### 5.4 Visualization Module

- Implemented in Python using the `rich` library for curses-free, colorized ASCII rendering.
- Receives events via the same vector-based event buffer from the SystemC side (drained after each simulation step).
- Visual layout mirrors Norton Disk Doctor: rows of block glyphs with legend, progress, and status fields.
- Export screenshot-like frames for automated tests (text-based golden files).

### 5.5 Data Structures and Specifications

#### 5.5.1 NAND Geometry Parameters

```cpp
struct NandGeometry {
    uint32_t dies;                    // Number of NAND dies (default: 4)
    uint32_t blocks_per_die;          // Blocks per die (default: 1024)
    uint32_t pages_per_block;         // Pages per block (default: 256)
    uint32_t page_size_bytes;         // Page data size (default: 16384)
    uint32_t oob_size_bytes;          // Out-of-band/spare area (default: 1024)
    uint32_t planes_per_die;          // Planes for parallel ops (default: 2)
};
```

**Derived Calculations:**

- Total capacity = `dies × blocks_per_die × pages_per_block × page_size_bytes`
- Block size = `pages_per_block × page_size_bytes`
- Default configuration: 4 dies × 1024 blocks × 256 pages × 16KB = **16GB raw capacity**

#### 5.5.2 NVMe Command Extension

```cpp
enum class NvmeOpcode : uint8_t {
    READ          = 0x02,
    WRITE         = 0x01,
    FLUSH         = 0x00,
    DATASET_MGMT  = 0x09,  // TRIM/deallocate
    IDENTIFY      = 0x06,
};

enum class NvmeStatus : uint8_t {
    SUCCESS                = 0x00,
    INVALID_OPCODE         = 0x01,
    INVALID_FIELD          = 0x02,
    CAPACITY_EXCEEDED      = 0x08,
    INTERNAL_ERROR         = 0x06,
    WRITE_FAULT            = 0x80,
    UNRECOVERED_READ_ERROR = 0x81,
};

enum class DataPattern : uint8_t {
    SEQUENTIAL_COUNTER = 0,  // Incrementing byte pattern
    LBA_HASH          = 1,  // Hash of LBA repeated
    ZEROS             = 2,  // All zeros
    ONES              = 3,  // All ones (0xFF)
    RANDOM            = 4,  // Pseudo-random based on seed
};

struct NvmeCommandExtension : public tlm::tlm_extension<NvmeCommandExtension> {
    uint16_t command_id;
    NvmeOpcode opcode;
    uint32_t namespace_id;
    uint64_t lba;              // Logical block address in units of sector_size_bytes (default 4096 bytes / 4KiB)
    uint16_t length;           // Number of logical blocks
    DataPattern pattern;       // Pattern for write/read verification
    uint32_t pattern_seed;     // Seed for random pattern generation
    NvmeStatus status;
    
    // TLM extension interface
    tlm_extension_base* clone() const override;
    void copy_from(const tlm_extension_base& ext) override;
};
```

#### 5.5.3 NAND Command Extension

```cpp
enum class NandCommandType : uint8_t {
    READ           = 0x00,
    READ_CACHE     = 0x31,
    PROGRAM        = 0x80,  // Page program
    PROGRAM_CACHE  = 0x15,
    ERASE          = 0x60,  // Block erase
    RESET          = 0xFF,
};

enum class NandStatus : uint8_t {
    SUCCESS        = 0x00,
    FAIL           = 0x01,  // Program/erase failure
    DATA_MISMATCH  = 0x02,  // Read verify mismatch
    CACHE_BUSY     = 0x20,
    READY          = 0x40,
    NOT_PROTECTED  = 0x80,
};

struct NandCommandExtension : public tlm::tlm_extension<NandCommandExtension> {
    NandCommandType command_type;
    uint8_t channel;           // Channel ID
    uint8_t die;               // Die select
    uint16_t block;            // Block address
    uint16_t page;             // Page within block
    uint8_t plane;             // Plane select for multi-plane ops
    DataPattern pattern;       // Pattern for verification
    uint32_t pattern_seed;     // Seed for pattern generation
    uint32_t length_bytes;     // Transfer length
    NandStatus status;
    
    // TLM extension interface
    tlm_extension_base* clone() const override;
    void copy_from(const tlm_extension_base& ext) override;
};
```

#### 5.5.4 NAND Block States

```cpp
enum class BlockState : uint8_t {
    FACTORY_BAD    = 0,  // Marked bad at manufacturing
    ERASED         = 1,  // Available for programming
    VALID          = 2,  // Contains valid data
    INVALID        = 3,  // Contains stale data (ready for GC)
    RUNTIME_BAD    = 4,  // Wear-out or program/erase failure
};

struct BlockMetadata {
    BlockState state;
    uint32_t erase_count;
    uint32_t program_count;
    std::vector<bool> valid_pages;  // Sized to geometry.pages_per_block at initialization
};
```

#### 5.5.5 Memory Management Contract

**Metadata-Only Design:**

- **No actual data transfer**: Simulator operates on metadata (LBA, length, pattern type) only.
- **Pattern-based verification**:
  - Writes store pattern metadata in NAND model's page metadata.
  - Reads verify that stored pattern matches expected pattern for given LBA.
  - NAND model internally generates/validates patterns without storing full page content.
- **Simple copy semantics**: Extensions contain only POD types (integers, enums) that are trivially copyable.
- **No buffer management**: No `std::shared_ptr`, no Python buffer protocol, no GIL concerns for data transfer.

**Pattern Verification Example:**

```cpp
// NAND model stores pattern metadata per page
struct PageMetadata {
    bool is_programmed;
    DataPattern pattern;
    uint32_t pattern_seed;
    uint64_t lba;  // For verification
};

// On write: store metadata
void nand_model::program_page(NandCommandExtension& cmd) {
    page_meta[block][page] = {
        .is_programmed = true,
        .pattern = cmd.pattern,
        .pattern_seed = cmd.pattern_seed,
        .lba = derive_lba_from_command(cmd)
    };
}

// On read: verify pattern matches
void nand_model::read_page(NandCommandExtension& cmd) {
    if (page_meta[block][page].pattern != cmd.pattern ||
        page_meta[block][page].pattern_seed != cmd.pattern_seed) {
        cmd.status = NandStatus::DATA_MISMATCH;
    }
}
```

**Benefits:**

- Eliminates complex memory management across Python/C++ boundary.
- Enables simulation of large capacities (TB-scale) without memory constraints.
- Simplifies debugging (pattern mismatches are explicit metadata comparisons).
- Allows focus on FTL logic and NAND behavior rather than data plumbing.

#### 5.5.6 Physical Page Address (PPA) and Direct Mapping

```cpp
struct Ppa {
    uint8_t channel;
    uint8_t die;
    uint8_t plane;
    uint16_t block;
    uint16_t page;
};
```

Phase 1 uses a direct-mapped addressing scheme from LBA to PPA using the configured geometry. A simple row-major mapping is applied across dies/blocks/pages. Writes that span page boundaries are split internally while honoring NAND program-order constraints.

#### 5.5.7 NandLatencyConfig

Define deterministic NAND operation latencies and thresholds; units are microseconds and map to `sc_time` via `sc_time(value, SC_US)`.

```cpp
struct NandLatencyConfig {
    uint32_t read_time_us;           // e.g., 80
    uint32_t program_time_us;        // e.g., 800
    uint32_t erase_time_us;          // e.g., 3000
    uint32_t read_disturb_threshold; // Optional; number of reads before disturb considered
    uint32_t wearout_threshold;      // Optional; erase count threshold for failures
};
```

#### 5.5.8 Simulation Configuration Highlights

- `sector_size_bytes` (default 4096). LBA units in commands are in this size.
- `global_seed` for deterministic runs; seeds pattern generators and any randomized behaviors.
- `nand_latency` of type `NandLatencyConfig`.

## 6. Build & Tooling Strategy

- **CMake** (minimum version 3.23) drives C++ build. Fetch external dependencies (`SystemC 3.0.2`, `PySysC`, `GoogleTest`) via `FetchContent` where possible; use `ExternalProject` only when upstream lacks CMake support.
- **uv** manages Python environments and dependencies (Invoke, rich for CLI rendering if desired).
- **Invoke tasks**:
  - `invoke bootstrap`: install/verify SystemC, PySysC build, configure uv environment.
  - `invoke build`: run CMake configure & build for core library.
  - `invoke test`: execute GoogleTest suites and Python unit tests.
  - `invoke lint`: run clang-format (check), clang-tidy, cpplint, and Python linters (pylint/flake8).
  - `invoke viz-demo`: launch sample simulation + visualization.
- Integrate `gcovr` to generate unified C++ code coverage reports; expose results via Invoke (`invoke coverage`) and archive outputs for CI.
- Treat compiler warnings as errors for all internal targets (`-Werror` via `target_compile_options`), while leaving third-party dependencies at their default warning settings.
- **Formatting & Static Analysis**:
  - Maintain `.clang-format` aligned with Google C++ style.
  - Configure `clang-tidy` targets in CMake (`CMAKE_CXX_CLANG_TIDY`).
  - Integrate `cpplint` via Invoke to enforce Google style specifics.
  - Python: leverage `pylint` plus `ruff` for formatting and linting while conforming to Google Python style.
  - Packaging: use `scikit-build-core` to integrate CMake builds with Python packaging; configure package-dir to `python/`.
  - Reproducibility: pin PySysC to a specific commit hash via `FetchContent`.

## 7. Testing Strategy

- **C++ Unit Tests**:
  - Each model resides in `src/<component>` with a matching `tests/<component>_test.cc`.
  - Use `gtest_main` and the [tlm2-gtestbench](https://github.com/cphurley82/tlm2-gtestbench) patterns to instantiate SystemC kernels inside GoogleTest fixtures.
  - Scope the SystemC kernel lifecycle per test or per test suite to avoid kernel reuse and interference between tests.
  - Provide mocks/stubs for downstream components when testing in isolation (e.g., host tests stub controller responses).

- **Python Tests**:
  - Use `pytest` for API-level validation (instantiation, simple I/O submission, visualization snapshot).
  - Ensure Python tests run after building bindings (Invoke orchestrates dependency order).

- **Integration Tests**:
  - Combine all three models to execute scripted workloads (sequential reads/writes, bad block handling).
  - Validate visualization output via deterministic text frames.

- **Continuous Verification**:
  - GitHub Actions workflow runs on push/PR to execute Invoke build, test, lint, format-check, and coverage tasks.
  - Cache heavy artifacts (SystemC, CMake, ccache) to reduce CI time.
  - OS matrix: ubuntu-latest and macos-latest; install `clang-format`/`clang-tidy` on macOS via Homebrew.
  - Track `gcovr` coverage reports in CI dashboards; begin with a lower threshold (e.g., 60–70%) and ratchet up as features stabilize.
  - Determinism: set a default global seed; verify golden visualization frames under CI.

## 12. Risks & Mitigations

### 12.1 SystemC Integration Complexity

**Risk**: PySysC binding issues or unexpected SystemC behavior.

**Mitigation**:

- Use synchronous execution model: Python directly controls `sc_start()` calls, eliminating threading concerns.
- Comprehensive integration tests validating PySysC bindings for each model.
- Incremental validation: test each component in isolation before full integration.
- Document PySysC API usage patterns and known limitations.

### 12.2 SystemC Dependency Management

**Risk**: SystemC 3.0.2 build complexity varies across platforms.

**Mitigation**:

- Document bootstrap process, supply scripts to build SystemC 3.0.2 locally.
- Provide Docker image with pre-built SystemC for reproducible environments.
- CMake `FetchContent` automates download and build; cache artifacts in CI.

### 12.3 Long-term Firmware Integration Complexity

**Risk**: DBT-RISE integration may require significant architectural changes.

**Mitigation**:

- Isolate interfaces and maintain clear separation between TLM models and higher-level firmware harness.
- Design controller model with pluggable backend (current: direct NAND access; future: firmware API).
- Prototype firmware integration as separate research spike before committing to design changes.

## 13. Error Handling and Exception Strategy

### 13.1 Python Exception Hierarchy

```python
class ToySSDException(Exception):
    """Base exception for all toyssd errors."""
    pass

class SimulationError(ToySSDException):
    """SystemC kernel or simulation execution error."""
    pass

class CommandError(ToySSDException):
    """Invalid command parameters or sequencing."""
    pass

class CapacityError(ToySSDException):
    """LBA out of range or insufficient space."""
    pass

class HardwareError(ToySSDException):
    """Simulated hardware failure (bad block, program/erase fail)."""
    pass
```

### 13.2 TLM Status Code Mapping

- TLM `tlm::TLM_OK_RESPONSE`: Success, check extension status code for completion details.
- TLM `tlm::TLM_GENERIC_ERROR_RESPONSE`: Maps to `SimulationError` in Python.
- TLM `tlm::TLM_INCOMPLETE_RESPONSE`: Command timeout or unexpected termination.
- Extension-specific status codes (NvmeStatus, NandStatus) populate exception messages.

Python exception mapping examples:

- NvmeStatus.INVALID_FIELD or NvmeStatus.CAPACITY_EXCEEDED → `CommandError`.
- NandStatus.FAIL or NandStatus.DATA_MISMATCH → `HardwareError` with detail message.
- Any unexpected combination with `tlm::TLM_OK_RESPONSE` but errorful extension status → `HardwareError`.

### 13.3 Error Recovery

- **Host Layer**: Retry transient errors (up to 3 attempts), raise `CommandError` on persistent failure.
- **Controller Layer**: Attempt block remapping on NAND program/erase failures, maintain bad block table.
- **NAND Layer**: Deterministic failure injection via configuration (e.g., `program_fail_rate=0.001`).

### 14.2 Integration Strategy

**Phase 1 (Current Design)**: Host Model → Controller Model (C++ FTL) → NAND Model

**Phase 2 (Firmware Integration)**:

The controller model evolves into a **complete SSD controller system** containing:

1. **Host Hardware Interface**:
   - NVMe submission/completion queue registers (MMIO).
   - Host-to-controller DMA engine.
   - Interrupt generation to firmware.

2. **RISC-V CPU (DBT-RISE)**:
   - Executes firmware from simulated boot ROM/flash.
   - Runs Zephyr RTOS with FTL application code.
   - Accesses both host interface and NAND hardware via memory-mapped registers.

3. **NAND Hardware Interface**:
   - Command/address/data registers for NAND operations.
   - Status registers for completion polling.
   - NAND-to-controller DMA for page transfers.

**Data Flow in Phase 2**:

```text
Host Model                Controller Model                  NAND Model
──────────                ────────────────                  ──────────
NVMe Write Cmd  ─────►    Host HW: Write to SQ register
                          ↓
                          Interrupt to RISC-V CPU
                          ↓
                          Firmware: Process command
                          ↓
                          Firmware: FTL L2P lookup/allocation
                          ↓
                          Firmware: Write NAND regs
                          ↓
                          NAND HW: Forward to NAND   ─────►  Page Program
                          ↓                           ◄─────  Status
                          Firmware: Read status
                          ↓
                          Firmware: Update L2P, post completion
                          ↓
NVMe Completion ◄─────    Host HW: CQ entry + interrupt
```

**Isolation Requirements**:

- **Current Phase 1**: Controller model contains direct C++ FTL implementation.
- **Future Phase 2**: Controller model becomes a **composite SystemC module**:
  - `host_interface` submodule (NVMe registers, TLM target socket).
  - `cpu_subsystem` submodule (DBT-RISE instance, memory map).
  - `nand_interface` submodule (NAND command/status registers, TLM initiator socket).
- NAND model interface remains **unchanged** (same TLM extension).
- Host model interface remains **unchanged** (same NVMe TLM extension).
- Clean separation allows parallel development: firmware can be developed independently once register specs are defined.

### 14.3 Design Decisions

- **Builder Pattern**: Use Python dataclasses for configuration (avoid DSL complexity).
- **Visualization**: Remain Python-based using `rich`; a vector-based C++ event buffer is sufficient for 16GB geometries.
- **NAND Detail**: Current implementation models block/page granularity; plane parallelism deferred to future work.

## 15. Initial Scope Decisions

- **NAND Latency Model**: The initial implementation will use simple, deterministic delays for NAND operations. Modeling statistical latency distributions (e.g., Gaussian/Weibull) is a long-term goal.
- **Performance Metrics**: The simulator will initially export core performance metrics: IOPS, bandwidth, and write amplification. Write amplification is defined as `WA = NAND_programmed_bytes / host_written_bytes`. Tail latency analysis is a long-term goal.
- **Workload Generation**: The first version will support synthetic workloads only. Trace replay support (e.g., from blktrace or FIO logs) is a long-term goal.
